## New script: `scene_duplicates_by_score.py`

It does the following:

1. **Loads scores** for one day directory from:
   - `collect_score.csv` (if present), using `musiq_score` or `calculated_score`, or  
   - `image_evaluation_results.json` (MUSIQ/AVA `musiq_score`).

2. **Sorts images by score** (highest first) and treats order as “best first.”

3. **Finds scene duplicates** using **imagededup’s CNN** (not hashing), so “same scene, different angle/zoom/composition” is detected. For each image in score order it only marks **lower-scoring** images as duplicates of that keeper, so the best shot per scene is always kept.

4. **Operates per day**: you pass a single directory (e.g. `2024-09-10`); only images under that directory are compared.

### Usage

```bash
# Install once (imagededup uses PyTorch under the hood)
pip install -r requirements_scene_duplicates.txt

# Run on a day folder (must already have scores from image_evaluator.py)
python3 scene_duplicates_by_score.py /path/to/2024-09-10

# Softer “same scene” (more pairs marked duplicate)
python3 scene_duplicates_by_score.py /path/to/day --threshold 0.5

# Use combined score from compare_image_quality_models.py
python3 scene_duplicates_by_score.py /path/to/day --score-attr calculated_score

# Save report and get only duplicate paths (e.g. for a delete/move script)
python3 scene_duplicates_by_score.py /path/to/day -o report.json --list-remove
```

### Options

| Option | Purpose |
|--------|--------|
| `--threshold` | Min cosine similarity to treat as same scene (default **0.6**). Lower → more duplicates. ~0.5 = “same place, different framing”; ~0.8 = stricter. |
| `--score-attr` | `musiq_score` (default) or `calculated_score`. |
| `--output` / `-o` | Write JSON with `keeper_to_duplicates` and `duplicate_to_keeper`. |
| `--list-remove` | Print one duplicate path per line (for piping into your own script). |

does that similarity threshold seem reasonable>?

---

**Cursor**


**0.65 is a reasonable default** for “same scene, different view” (different angle/zoom/composition).

- **imagededup’s default** for CNN is **0.9**, which is for near-duplicates (almost the same crop). You’d miss a lot of “same place, different framing” pairs at that level.
- **0.5** “allows large deviation” and is often used for different viewpoints; it can pull in more false positives (different scenes that look similar).
- **0.65** sits between them: loose enough to catch same-scene shots with different framing, but a bit stricter than 0.5 to reduce false pairs.

**Practical tuning:**

- If you see **obvious same-scene pairs not being grouped** (e.g. wide vs zoomed of the same spot), try **0.55–0.6**.
- If you see **different scenes grouped together**, try **0.7–0.75**.

You can override anytime with `--threshold`, e.g.:

```bash
python3 scene_duplicates_by_score.py /path/to/day --threshold 0.6
```

why were the imports done within functions or buried within try catch code and not just put at the beginning of the program?

**Cursor**


I don’t know the original author’s intent; the code may have evolved that way. Common reasons this pattern shows up:

1. **Lazy imports** – Importing inside a function defers loading a heavy library (e.g. `imagededup`, TensorFlow) until that code runs. So `--help` or other code paths that don’t need it start faster. The downside is that a missing dependency isn’t reported until that path runs.

4. **Incremental changes** – EXIF might have been added later with “import in the function that needs it” and “catch errors so we don’t crash,” without a separate check for “is the package installed?”

So: the in-function imports and try/except were likely for lazy loading and/or defensive handling of bad files, but they had the side effect of hiding a missing dependency. Putting the imports at the top is the right fix: missing packages fail immediately with a clear error, and try/except can be limited to real runtime failures (e.g. per-file I/O) if needed.
